# GroupCOT — Архитектура управления логитами и семантического конструктора

> Документ описывает архитектуру подсистемы управления генерацией на уровне
> логитов: послойную фильтрацию, исключение языка, концептуальный
> «семантический конструктор» (авто-построение масок по смыслу) и инструмент
> измерения полноты семантического поля. Часть описанного уже реализована,
> часть — спроектирована и помечена как *предлагаемая*.

Статусы:
- `[✓]` — реализовано и работает в коде.
- `[✑]` — спроектировано, к реализации не приступали.

---

## 1. Контекст и основная идея

GroupCOT дополняет языквую модель **гипертекст-контекстом**, построенным на
**коммутативной группе** над эмбеддингами текста (`Cyclic(n)` / `Vector(dim)`).
Связанные фрагменты компонуются групповыми операциями, подтягиваются в активный
контекст (retrieval каждые N шагов) и управляются через:

- **constrained decoding** — GBNF-грамматики (шага `element`, финальный `final_json`);
- **group-level logit filtering** — перенаправление/маскировка токенов на уровне логитов;
- **трёхканальную фильтрацию** подтянутого контекста.

Цель подсистемы управления логитами — дать **точный и семантически осмысленный
контроль** над тем, что модель *может вывести*, не теряя понимания темы.
Наблюдение, породившее эту архитектуру: при исключении китайского языка модель
всё ещё *понимает* вопрос и отвечает по-английски, обращаясь к тому же
смысловому полю, — то есть мы гасим **токены**, а не **понятие**. Отсюда шаг к
управлению произвольными семантическими конструкциями.

## 3. Подсистема управления логитами (layered filtration)

### 3.1 Исключение языка `[✓]`

Два механизма, оба для бэкенда `llamacpp`:

1. **Маскировка token-ID** — предвычисленные `lang` token-ID перенаправляются
   через `LogitsProcessor` (`LanguageRedirect` в `engine/processors.py`).
2. **Runtime blocked-ranges** — because BPE может упасть на byte-токены,
   которые всё равно декодируются в CJK в контексте, генерация выполняется
   вручную (`llm.eval` + `llm.eval_logits`) с посимвольным фильтром
   (`DEFAULT_BLOCKED_RANGES`) и откатом KV-кэша.

**Критический баг (исправлен) `[✓]`:** предыдущий подход только через
`logits_processor` работал **только при `temperature=0`** (в `llama-cpp-python`
0.3.35 хук `logits_processor` применяется к топ-K кандидатам и расходится по
temperature). Runtime blocked-ranges с ручным сэмплингом (`_sample_token`) и
откатом (`_find_rollback`) работает при **любой temperature**.

Ключевые точки `engine/llamacpp.py` `[✓]`:
- `DEFAULT_BLOCKED_RANGES` — диапазоны CJK.
- `generate(..., blocked_ranges=None)` — роутит в `_generate_filtered`.
- `_is_blocked_char`, `_count_blocked`, `_find_rollback`, `_sample_token`,
  `_generate_filtered` — ручной eval-цикл с откатом KV-кэша.

### 3.2 Трёхканальная фильтрация `[✓]`/контекст

Фильтрация контекста при `pull` (правила `filters` из `config.yaml`) + фильтрация
логитов (язык/концепт) + грамматическое ограничение (GBNF). Эти каналы
независимы и компонуются в `LogitsProcessorChain`.

## 3.3 Дуальная операция: не только исключение, но и включение `[✑]`

Управление логитами **симметрично**. Наряду с исключением смысла нужна и
обратная операция — **включение / притяжение / удержание** нужного смысла.
Без неё конструктор умеет лишь *запрещать*, но не *направлять* модель в нужное
смысловое поле. Текущая архитектура (§3.1, §4, §5) описывает преимущественно
исключение; здесь добавляется дуальное направление.

Две примитивные операции над полем F_C концепта c:

- **Exclusion (suppress)** — `logits[t] = -∞` для `t ∈ F_C`: убрать смысл из
  достижимых выходов. Реализуется как `ConceptSuppress`; частично уже есть
  `LanguageRedirect` (перенаправление запрещённых токенов на разрешённые того же
  смысла, `[✓]`).
- **Inclusion (attract / constrain)** — три формы:
  1. *Bias / притяжение*: `logits[t] += w · sim(emb(t), c)` — сдвинуть
     распределение в сторону концепта без жёсткого запрета остального.
  2. *Whitelist / ограничение полем*: разрешить **только** токены поля —
     `logits[t] = -∞` для `t ∉ F_C`. Генерация *ограничена* полем — дуально к
     исключению («только F_C» вместо «всё, кроме F_C»).
  3. *Redirect* (есть `[✓]`): перенаправить с запрещённого на разрешённый токен
     того же смысла.

**В групповом пространстве обе операции линейны и симметричны:** exclusion =
вычесть проекцию на запрещённое направление, inclusion = добавить проекцию на
желаемое. Коммутативность делает их компонуемыми и взаимно согласованными через
групповые операции (объединение/дополнение полей). Это превращает управление
смыслом в единый механизм: **вектор правил** `(поле, знак, вес)`, где знак
различает исключение (−) и включение (+).

**Следствия для остальных модулей:**
- `ConceptConstructor` порождает **оба** типа правил (`exclude` / `include` /
  `attract` / `constrain`); `ConceptSpec` расширяется полями `mode` и `weight`.
- `SemanticFieldMeter` получает **дуальную метрику** (см. §6): для inclusion —
  *adherence / in-field probability* = `Σ_{t∈F_C} p_t` (доля вероятности модели,
  приходящаяся на желаемое поле), плюс precision/recall по полю.

## 4. Семантический конструктор — концептуальные варианты `[✑]`

«Конструктор» — механизм, который по теме/интенту **сам строит**, какие логиты
связаны с этой темой, и исключает их при необходимости. Четыре варианта:

| # | Вариант | Суть | Плюсы | Минусы |
|---|---------|------|-------|--------|
| V1 | Статический лексикон | концепт → явный список token-ID | детерминированно, объяснимо, готово | хрупко к перефразировке, не ловит поле |
| V2 | Сем. подобласть в группе | сид → центроид в группе → ближайшие токены (`Puller`) → маска | ловит поле, токенизационно-независимо, переиспользует группы | нужен прототип, подбор радиуса |
| V3 | Динамический self-query | модель сама формулирует спецификацию запрета → компиляция в маску | полностью динамично, адаптивно | двухшаговость, латентность, недетерминированность |
| V4 | Обучаемый concept-erasure head | голова на hidden states флагует запрещённый концепт | гибко, ловит тонкие смыслы | нужны данные/обучение, избыточно |

**Выбор `[✑]`: V2 как основной + V1 как жёсткий слой безопасности.**
Обоснование: V2 напрямую реализует «конструктор → токен-подпространство →
исключить», 80% инфраструктуры уже есть (`TokenGroup`, `Puller`, эмбеддинги,
логит-процессоры), детерминированно и быстро (компилируется один раз на
концепт). V3 — «видение будущего» (модель сама формулирует прототип); V4 —
избыточен.

## 5. Вариант 3 — детальная архитектура `[✑]`

### 5.1 Поток данных (фазы)

```
[Фаза 0] Интент (естеств. язык)
            "запрети [768,758] для тензорных слоёв"
                         │
                         ▼
[Фаза 1] Self-query / конструктор-промпт ──→ ConceptSpec (JSON)
            модель генерит: lexicon / prototypes / allowed
                         │
            ┌────────────┴─────────────┐
            ▼                          ▼
[Фаза 2а] Лёгкая компиляция      [Фаза 2б] Полная компиляция
  tokenize(lexicon) → Set[int]     embed(prototypes/allowed) →
                                   центроид/направление → Puller →
                                   ближайшие токены → Set[int]
                         │                          │
                         └────────────┬─────────────┘
                                      ▼
[Фаза 3] ConceptSuppress(Set[int]) → LogitsProcessorChain
          → generate() (маска накладывается, temperature>0 ок)
                         │
                         ▼
[Фаза 4] (опц.) уточняющий цикл: SemanticFieldMeter.leakage > Y%
          → ещё один self-query с примером утечки → расширение B
```

### 5.1.1 Фаза 4 — целые предложения/парафраз, не только слова `[✓]` (механизм; качество = качество embed())

Токенная маска (V3a/V3b) в принципе не может поймать концепт, который не сводится
к словам — «поехать на море» и «поехать на океан»/«поехать на рыбалку» почти не
пересекаются по токенам, но это один смысл. Логит-процессор видит только
следующий токен и не может «знать», куда клонится ещё не дописанное
предложение — значит контроль на этом уровне нужен *после* генерации фрагмента,
не вместо неё.

Реализовано в `engine/guarded_generation.py`:

- **`SentenceConceptGuard`** — классифицирует целое предложение по сходству
  эмбеддинга с `spec.prototypes` концепта (это **целые примеры предложений**,
  не лексикон слов): `"поехать на море"`, `"поехать на океан"`, `"поехать на
  рыбалку"` — один концепт; `"поехать в сад"`, `"поехать в лес"` — другой.
- **`generate_guarded(engine, prompt, guard, ...)`** — генерирует small
  chunk'ами, на каждой законченной фразе спрашивает guard; если совпадение —
  **не** повторяет попытку с той же маской (при `temperature>0` это не
  гарантирует уход от того же смыслового кластера — распределение не
  изменилось), а по примеру утечки делает **ещё один self-query**
  (`ConceptConstructor.construct` на тексте отклонённого предложения) →
  расширяет `concept_ids` → перегенерирует **ту же позицию** с более широкой
  маской. Каждый отказ детерминированно сужает пространство, а не повторяет
  сэмплирование того же распределения. Лимит `max_rejections` на весь вызов —
  чтобы не уйти в бесконечный цикл, если модель упорно тянется к теме.
- Тесты (`tests/test_guarded_generation.py`, 5/5 зелёные) на детерминированном
  fake-engine: классификация, цикл reject→widen→accept, `gave_up` после
  исчерпания лимита, passthrough, когда ничего не совпало.

**Находка при первой проверке на реальной модели (Qwen3VL как источник
`embed()`):** механизм запускался и работал без ошибок, но **порог
`threshold` был неюзабелен** — ложные совпадения набирали *больше*, чем
истинное (`"Go hiking in the mountains"` → 0.935 vs истинное `"Let's go to
the ocean"` → 0.975, зазор почти нулевой). Прямое продолжение анизотропии
из §5.5 — она ломает не только поиск ближайших токенов, но и попарное
сравнение целых предложений.

**Решение — dual-engine: отдельная embedding-модель, не generative.**
`VocabIndex` и `ConceptConstructor.compile`/`_compile_semantic` теперь
принимают `embed_engine` (генерация и токены — по-прежнему с основной
модели, эмбеддинги — с отдельного движка); `SentenceConceptGuard` и так был
engine-agnostic — ему просто передаётся embedding-движок напрямую.

**Проверено `[✓]`: `multilingual-e5-small` (GGUF, q8_0, ~126MB,
`TwinSunsLLC/multilingual-e5-small-gguf`), рядом с Qwen3VL, оба через
`LlamaCppEngine`:**
- Изотропия заметно лучше: реальный градиент похожести вместо плоского шума
  (англ. `cat`: cats 0.972, kitten 0.933, dog 0.910, http 0.833 — монотонно
  убывает по смысловой близости, у Qwen всё было ~0.98-0.99 без разбора).
- Одна ловушка: короткие прототипы, разделяющие шаблон фразы («поехать в
  X»), дают завышенное сходство по шаблону, а не по смыслу (`"поехать в
  лес"` против единственного прототипа `"поехать на море"` → 0.92). Лечится
  **несколькими по-разному сформулированными прототипами на концепт +
  усреднение**, а не взятие максимума — `SentenceConceptGuard` получил
  параметр `aggregation="mean"` (default) / `"max"`; тест
  `test_sentence_concept_guard_mean_vs_max_aggregation` фиксирует эффект.
- `guard.classify()` на реальных RU-фразах при `threshold=0.90,
  aggregation="mean"`: 5 из 6 верно (ложноотрицательная — не типовая
  формулировка "давай съездим на рыбалку в выходные" без слова "поехать").
- **Полный цикл reject→widen→regenerate воспроизведён на реальных моделях**
  (не только на fake-engine): промпт «куда поехать к воде отдохнуть» →
  первая генерация `"Поехать на выходные на побережье Черного моря — идеально
  для отдыха у воды."` → отклонено guard'ом → self-query по утечке →
  `concept_ids` расширился на 30 токенов → перегенерация →
  `"Поезжайте в горный озеро — там всегда спокойно и чисто."` — принято,
  моря/океана/рыбалки нет. ~41с на CPU (несколько вызовов модели
  последовательно на каждый чанк — не оптимизировано на скорость: каждый шаг
  `generate_guarded` заново эвалюирует `prompt + accepted` с нуля, KV-кэш
  между чанками не переиспользуется, см. §5.4).

**Итог:** механизм рабочий на реальных моделях, не только в тестах. Остаётся
не идеальным (ложноотрицательные при непривычной формулировке, побочные
грамматические огрехи от токенной маски вроде «горный озеро» вместо «горное
озеро», задержка на CPU) — но это уже настройка порога/промптов, а не
отсутствие сигнала.

### 5.2 Контракты модулей `[✑]`

- **`ConceptConstructor`** (новый):
  - `construct(intent: str) -> ConceptSpec` — вызов `LlamaCppEngine.generate`
    с мета-промптом «ты — конструктор масок, выдай JSON-спецификацию, не решай
    задачу». Возвращает `ConceptSpec{concept, mode, weight, lexicon[],
    prototypes[], allowed[]}`, где `mode ∈ {exclude, include, attract,
    constrain}` (см. §3.3 — конструктор порождает **оба** направления:
    запретить смысл и/или направить в него).
  - `compile(spec: ConceptSpec) -> Set[int] | bias` — V3a: `tokenize` каждой
    фразы лексикона; V3b: `embed` прототипов + `Puller` по групповому расстоянию.
    Для `exclude`/`constrain` результат — `Set[int]` (маска); для `attract` —
    вектор смещения логитов по полю. Результат кэшируется на сессию/правило.

- **`ConceptSuppress(Set[int])`** (в `engine/processors.py`, `[✑]`):
  - `logits[token_ids] = -inf`. Работает при `temperature>0` (как `LanguageRedirect`,
    но точечно по ID, дешевле посимвольного rollback).

- **`LlamaCppEngine.generate`** — добавляется параметр `concept_ids: Set[int] | None` `[✑]`;
  при наличии цепляется `ConceptSuppress` в `logits_processor` (или лёгкий путь
  маскировки по ID в `_generate_filtered`).

- **`context/loop.py`** — `_make_logits_processor()` расширяется цепочкой; при
  наличии интента вызывает Фазу 1→2 и кэширует `Set[int]`.

- **`cli.py` / `gui.py`** — приём интента (`--concept "..."` / вкладка
  «Конструктор»), отображение скомпилированного `Set[int]` с кнопкой «утвердить».

### 5.3 Пример (тензоры 768/758) `[✑]`

1. Интент: «не выдавай [768,758] для слоёв».
2. Self-query → `lexicon: ["768","758","[768, 758]"]`, `prototypes` про неверные размеры.
3. Лёгкая компиляция: токенизируем → `Set[int]` (числовые `768`, `758`, составные).
   Полная: эмбеддим прототип → подтягиваем смежные «тензоры/слои в этом смысле».
4. Маска наложена; модель понимает тему, но **не может вывести запрещённую
   подпоследовательность** → уходит в корректное `[768, 2068]`.

### 5.4 Компромиссы и смягчение `[✑]`

- *Недетерминированность self-query* → Фаза 1 с низкой temperature/greedy, кэш, утверждение в GUI.
- *Латентность* → конструктор считается один раз на правило; при старте GUI — в фоне.
- *Широта маски / переподавление* → лимит `|Set[int]|`; Вариант 1 как жёсткий предел; видимость маски в GUI.
- *Безопасность* → критические токены блокируются явным лексиконом; self-query только *расширяет*, не *снимает*.

### 5.5 Лёгкая vs полная версия

Рекомендуется начать с **лёгкой** (self-query → lexicon → `Set[int]`): даёт весь
эффект «модель сама строит маску», не требует индекса эмбеддингов словаря и
переиспользует `logits_processor`. Полная (эмбеддинг-подпространство) —
когда нужно ловить смысловое поле целиком, а не только явные фразы.

**Полная версия (V3b) реализована `[✓]`** — `engine/vocab_index.py::VocabIndex`
+ `ConceptConstructor.compile(spec, vocab_index=...)`:

- `VocabIndex.build()`: сканирует словарь модели, берёт до `max_candidates`
  «словоподобных» токенов (алфавитные, ≥2 символа, дедуп по
  `lower().strip()`) **в порядке token-ID** — для BPE-словарей это približает
  сортировку по частоте (merges учатся от частого к редкому), так что кап без
  явной частотной таблицы всё равно оставляет частую лексику. Эмбеддит их
  через `engine.embed_batch` (по умолчанию — последовательные вызовы, см.
  ниже), L2-нормализует, кэширует на диск (`~/.cache/groupcot/vocab_index/`,
  ключ = hash(model_path, vocab_size, max_candidates)).
- `ConceptConstructor._compile_semantic`: эмбеддит `spec.prototypes +
  spec.lexicon` (или `spec.concept` как fallback), берёт top-k ближайших
  токенов по косинусу из индекса на seed, объединяет с V3a-лексиконом;
  `spec.allowed` вычитается из расширения (safety net, §5.4).
- CLI: `--semantic-concept` (+ `--concept-topk`, `--concept-min-sim`,
  `--concept-vocab-size`) в `cli.py::_build_concept_ids`.
- Тесты: `tests/test_concept.py` — `VocabIndex` (build/dedup/cache-roundtrip/
  nearest) и `compile_semantic` (ловит морфологические варианты, уважает
  `allowed`) на детерминированном fake-engine с контролируемым игрушечным
  эмбеддинг-пространством. 12/12 зелёные.

**Найденная и исправленная реальная проблема:** `llama-cpp-python` 0.3.35's
`create_embedding(list[str])` (batch-режим) возвращает **испорченные**
векторы — каждый элемент после первого оказался тем же float-буфером первого
элемента, прочитанным со сдвигом на индекс, а не независимым эмбеддингом
(подтверждено эмпирически: `embed_batch(["cat","dog","http"])["dog"][:5] ==
embed_batch(["cat"])["cat"][1:6]`). `LlamaCppEngine.embed_batch` теперь делает
по одному вызову `create_embedding` на текст — медленнее (~0.17с/вызов на
CPU), но корректно.

**Открытое ограничение (эмпирическое, не баг):** на реальной модели
(Qwen3VL-4B-Instruct, `embedding=True`, дефолтный pooling) косинусное сходство
между случайными словами практически не различимо (`cos(cat, dog) ≈ 0.993`,
`cos(cat, http) ≈ 0.989` — то есть почти всё в узком конусе, классическая
анизотропия нетюненных decoder-LM эмбеддингов). Центрирование средним по
словарю (400+ слов) эффект не даёт. Из-за этого ближайшие соседи по
`VocabIndex.nearest()` на этой модели зачастую оказываются случайными
сабворд-фрагментами, а не семантически близкими словами («cats»/«kitten» для
«cat»). **Инфраструктура и алгоритм корректны** (проверено на контролируемом
fake-engine и юнит-тестами) — узкое место в качестве `embed()` этой
конкретной generative-модели, не обученной как embedding-модель. Практический
путь вперёд: (а) отдельная embedding-модель (BGE/E5/nomic GGUF) как источник
`embed()`, (б) whitening/PCA-декорреляция по большому фоновому набору вместо
простого центрирования средним, (в) дешёвая нейтральная альтернатива —
морфологическое расширение лексикона (стемминг/плюрализация) вместо
embedding-поиска.

## 6. Детерминатор полноты семантического поля `[✑]`

Инструмент измерения того, насколько маска закрывает семантическое поле
концепта. Операционализация:

- **F_C** — семантическое поле концепта C (множество принадлежащих ему токенов).
- **B** — заблокированные ID; **B = B_lex ∪ B_exp** (жёсткая + расширенная части).

Величины:
1. **coverage** = `|B ∩ F_C| / |F_C|` — доля поля, реально погашенная.
2. **Соотношение «конкретная блокировка / всё поле»**:
   - `lexicon_pct = |B_lex ∩ F_C| / |F_C|` (вклад точечной блокировки);
   - `expanded_pct = |B_exp ∩ F_C| / |F_C|` (вклад расширения);
   - их отношение показывает, не «расползлась» ли маска.
3. **Процент от поля целиком** = coverage в %; плюс **leakage** (динамическая):
   `Σ_{t∈F_C\B} p_t` — доля вероятностной массы, остающейся в незаблокированной
   части поля при *текущих* логитах.
4. **Дуальная метрика для inclusion** (§3.3): `SemanticFieldMeter` измеряет не
   только подавление, но и *удержание* смысла:
   - *adherence / in-field probability* = `Σ_{t∈F_C} p_t` — какая доля
     вероятности модели приходится на **желаемое** поле (насколько модель
     «держится» нужного смысла);
   - *inclusion recall* = `Σ_{t∈F_C} p_t` (охват поля в выводе) и
     *inclusion precision* = `|allowed ∩ F_C| / |allowed|` (разрешённое
     действительно лежит в поле). Вместе с `coverage`/`leakage` это даёт полную
     картину: «насколько убрали плохое» и «насколько удержали хорошее».

**`SemanticFieldMeter`** `[✑]` (новый модуль):
- `coverage(concept_seed, blocked_ids, radius) -> {field_size, blocked_in_field, coverage_pct, lexicon_pct, expanded_pct}`.
- `leakage(logits, concept_seed, blocked_ids) -> pct`.
- Пороги: `coverage_pct < X` → расширить маску; `leakage_pct > Y` → триггер Фазы 4 (уточняющий self-query).

### 6.1 Роль коммутативных групп (ключевая)

Группа — не декорация, а **геометрия и мера**, в которой «поле» определено строго:

1. **Поле = область в группе.** Концепт — вектор `c` в `Vector(dim)`/`Cyclic(n)`.
   Поле — шар радиуса r вокруг `c` в групповой метрике:
   `F_C = { t : dist(g(t), c) < r }`. Это не эвристика cosine, а область в группе.
2. **Точный «процент от поля».** В конечной группе есть считающая мера: если F_C
   выражается через групповую структуру (подгруппа/косет/подкуб), то `|F_C|` и
   `|B ∩ F_C|` считаются **точно** (порядок группы, индекс подгруппы, размер
   косета). Coverage = отношение мощностей — буквально «процент от поля».
3. **Коммутативность = точные операции над полями.** Объединение/пересечение/
   дополнение областей концептов — групповыми операциями. Это даёт единый
   измеритель полноты для **любой комбинации** конструкторов (итоговое поле
   `F_{C1} ⊕ F_{C2}` считается тем же meter'ом).
4. **Переиспользование.** `Puller` уже ищет ближайшие токены по групповому
   расстоянию → поле УЖЕ задано группой (`TokenGroup` задаёт группу и метрику).
   Meter берёт ту же геометрию, добавляя лишь подсчёт мощностей.

### 6.2 Статический vs динамический режим `[✑]`

- **Статический coverage** — прекомпьютится при построении концепта; отвечает
  «маска ли покрывает поле?» (структура маски).
- **Динамический leakage** — по логитам на шаге; отвечает «сколько вероятности
  утекает в поле сейчас?» (поведение модели под маской). Ловит случай, когда
  модель понимает смысл и пытается выдать его другими токенами.

## 10. Include ↔ retrieval: дуальность Фазы 4 и динамический контекст `[✓]` (механизм; сила притяжения — открытый вопрос)

До этой сессии include/attract работал только на уровне токенов в обычных
concept-правилах (§6.4) — guard (Фаза 4, §5.1.1) был жёстко заточен под
exclude: «похоже на запрещённое → отклонить». Симметричная операция —
«недостаточно похоже ни на одно из требуемых → отклонить» (уход от темы,
а не приближение к запрещённой) — не существовала. Вторая часть: retrieval
(`Puller`/`Store`/`AutoPullLoop`, §2) и семантический конструктор жили
отдельно друг от друга — Run-цикл ничего не знал про concept_ids/attract_ids,
а чат ничего не знал про подтянутый контекст.

### 10.1 Include-guard в Фазе 4 `[✓]`

`engine/guarded_generation.py`:

- **`GuardViolation`** (`NamedTuple`, поля `spec, similarity, kind="exclude"`)
  — заменил старый `tuple[ConceptSpec, float]`; порядок полей сохраняет
  обратную совместимость (`violation[0]`/`violation[1]` работают как раньше
  для exclude-only кода), `kind` — новое поле.
- **`SentenceConceptGuard.classify()`** теперь дуален по `spec.mode`:
  - `exclude`/`constrain` — как раньше, отклонить при сходстве **выше**
    `threshold`;
  - `include`/`attract` — отклонить, если сходство **ниже**
    `include_threshold` (по умолчанию = `threshold`) до **любого** из
    include-концептов — несколько include-концептов работают через OR
    (достаточно совпасть хоть с одним, не со всеми). Exclude проверяется
    первым — при конфликте (текст одновременно «слишком похож на
    запрещённое» и «не дотягивает до требуемого») побеждает запрет.
- **`generate_guarded()`** — две ветки виджена, принципиально разные, потому
  что известно про concept разное количество:
  - exclude: как раньше — self-query по утечке → расширение `concept_ids`
    (маска только растёт, потому что заранее не знаем формулировку утечки);
  - include: цель уже полностью задана `spec.prototypes`/`lexicon` — не
    нужен self-query, `attract_ids` компилируется **один раз** заранее
    (`ctor.compile(spec, vocab_index=...)` для каждого include-концепта).
    Повторный уход от темы просто **усиливает** `attract_weight` на
    `attract_weight_step`, с потолком `max_attract_weight` (по умолчанию
    `3×attract_weight`) — без потолка неограниченный вес на узком множестве
    токенов уводит модель в зацикленный повтор одного токена (см. §10.3).
  - Счётчик отказов для `gave_up` — **на позицию** (сбрасывается при каждом
    принятом предложении вместе с весом), не кумулятивно на весь вызов: для
    include-режима 2 отказа на предложение — нормальный паттерн (вес каждый
    раз стартует заново), а не повод сдаться после первых 6 предложений
    длинного ответа. (Это исправление всплыло через тест — юнит-тест на
    эскалацию веса ловил `gave_up=True` там, где по смыслу не должно было.)
- Тесты (`tests/test_guarded_generation.py`, 11/11): классификация exclude
  vs include, OR-семантика нескольких include-концептов, приоритет exclude
  при конфликте, эскалация веса без порчи `concept_ids`, потолок эскалации.

### 10.2 Context → attract: связка retrieval и include `[✓]`

`context/attractor.py` (новый модуль) — три функции, без обращения к
`ContextState.active_ids()` напрямую (это `set`, без порядка — recency
даёт только `AutoPullLoop`'s собственный `order`, поэтому функции берут
`node_ids` явным параметром, а не `state`):

- `active_node_texts(store, node_ids, max_nodes=None)` — текст последних
  `max_nodes` узлов по данному порядку.
- `context_attract_ids(store, node_ids, vocab_index, ...)` — переэмбеддивает
  текст активных узлов через `vocab_index.embed_query` (**не** переиспользует
  `Node.embedding` — оно почти наверняка из другого движка/пространства, см.
  анизотропию в §5.5, сравнивать нельзя) → `VocabIndex.nearest()` → union.
- `context_include_spec(store, node_ids, ...)` — `ConceptSpec(mode="include")`
  с прототипами = текст активных узлов, для `SentenceConceptGuard`.

`context/loop.py::AutoPullLoop` — новый опциональный параметр `vocab_index`.
Если задан: после каждого pull-цикла `attract_ids` пересчитывается из
`order` (recency-список, уже был в цикле) и передаётся в `engine.generate(...)`
на следующих шагах — цель притяжения обновляется автоматически вслед за
Puller'ом, без отдельного состояния. `None` по умолчанию — поведение без
`vocab_index` не меняется. Тесты (`tests/test_attractor.py` 7/7,
`tests/test_loop.py` — 2 новых): `attract_ids` пуст до первого pull-цикла,
непуст после, полностью отсутствует без `vocab_index`.

**Это и есть механизм «бесконечного» контекста**: `Store` растёт без
ограничения, `Puller` держит активное окно маленьким, а `context_attract_ids`
не даёт генерации «забыть» про то, что реально подтянуто, даже когда полный
текст давно не помещается в промпт — целится не в фиксированную тему,
а в то, что живо в окне *прямо сейчас*.

### 10.3 Реальная находка: attract — слабый инструмент для жёсткого разворота темы

Проверка на реальных моделях (Qwen3VL + e5, dual-engine) вскрыла две вещи
подряд, обе важные:

1. **Масштаб весов был неверный на порядки.** Дефолт `attract_weight=5.0`
   (унаследован из ранних сессий) на самом деле для этой модели гарантирует
   зацикленный повтор одного токена: логиты модели имеют `std≈2.9`, типичный
   разрыв топ-1/топ-2 — `0.2–1.0`. Добавка `+5` (тем более `+10..12` после
   эскалации) не «подталкивает» — она делает выбранные токены почти
   детерминированными на **каждой** позиции чанка, не только там, где это
   уместно по смыслу. Результат на практике: `"...еда еда еда еда..."`,
   `"...тттттттт..."`. Калибровка веса под масштаб логитов конкретной модели
   — обязательна, дефолт `5.0` не универсален.
2. **Даже с откалиброванным весом (без зацикливания) attract не смог
   развернуть генерацию на жёстко контрастную тему** (промпт «дай совет на
   сегодня» → просили удерживать «кулинария»; get 6 отказов подряд,
   `gave_up=True`, ни одного принятого предложения). Это не баг — это
   реальный предел точечной логит-добавки: она хорошо **подавляет**
   конкретные нежелательные токены (exclude), но плохо **навязывает** целую
   тему при сильном естественном тяготении модели в другую сторону. Просадка
   вероятности у знакомого продолжения обычно больше, чем то, что способна
   перевесить добавка к горстке токенов, не разрушив естественность текста.

**Вывод:** механизм (классификация, дуальное ветвление, потолок эскалации,
context-linking) корректен и покрыт тестами — эмпирически подтверждённое
узкое место в другом: logit-level attract — инструмент для **удержания**
уже вероятного направления (в т.ч. context-attract для retrieval, где цель
обычно и так близка к тому, о чём модель уже говорит), а не для **разворота**
на контрастную тему. Для жёсткого разворота нужен другой канал — скорее
всего prompt-level инструкция (вставить в системный промпт то, что подтянул
`Puller`, явно), а не только logit-bias поверх него.

### 10.4 Как ставить эксперимент проверки улучшения

- Датасет задач с явным критерием «должен остаться в теме X» или «должен
  использовать факты A/B/C из подтянутого контекста».
- A/B на одинаковых промптах/seed: с/без context-attract (`vocab_index=None`
  vs заданный).
- Метрики:
  - **adherence** = среднее сходство сгенерированных предложений с
    прототипами активного контекста — уже считается `SentenceConceptGuard.classify()`
    внутри, нужно только логировать `similarity`, не только факт нарушения
    (частичный `SemanticFieldMeter`, §7, без реализации всего модуля);
  - **rate дрейфа** — доля предложений ниже `include_threshold`, с/без
    привязки к контексту, за длинный диалог;
  - LLM-judge/человек на слепом сравнении пар;
  - для фактологического сценария — recall фактов, присутствовавших только
    в retrieved-узлах, не в последних N сообщениях истории.
- Как и раньше — вся метрика имеет смысл только с нормальной
  embedding-моделью (§5.5); на «сыром» `embed()` генеративной модели
  разделение по смыслу отсутствует у adherence точно так же, как у guard'а.

### 10.5 Коммутативные группы здесь не используются

Честно: `context_attract_ids`/`context_include_spec`/`SentenceConceptGuard`
работают на сыром cosine по эмбеддингам, не через `TokenGroup`/групповую
метрику — то же самое, что уже отмечено в §6.1/§5.5 про V3b и Фазу 4 в целом.
Группы в этой связке используются только там, где были и раньше:
`ContextState.h` (агрегация активного контекста через `Cyclic`/`VectorAdd`)
и `TokenGroup` для языковых масок. Разговор про «точную considering-меру
поля через coset» (§6.1) остаётся нереализованным видением, не тем, что
реально работает в `context_attract_ids` сегодня.

## 11. Отказ от `server`-бэкенда (`ServerEngine`, remote `llama-server`) `[✓]`

`ServerEngine` (HTTP-клиент к отдельному процессу `llama-server`) удалён из
кода целиком. `llamacpp` (in-process `llama-cpp-python`) — единственный
реальный бэкенд; `mock` остаётся для тестов.

**Почему.** Server-бэкенд изначально был равноправной альтернативой
`llamacpp` (§2 в ранних версиях этого документа), но почти всё, что
реализовано в §3-§10 — концептный конструктор, Фаза 4, dual-engine,
`context_attract_ids` — требует возможностей, которых у HTTP API
`llama-server` в принципе нет:

- **Сырые logits перед сэмплированием.** `logits_processor` (pre-sampling,
  `LogitsProcessorChain`) — то, на чём стоит вся токенная фильтрация
  (§3.1-§3.3) — сервер не поддерживает вообще; единственный канал у него —
  `logit_bias`, аддитивный dict, применяемый post-hoc и только к
  `/completions` (`/chat/completions` его игнорировал).
- **Ручной сэмплинг с откатом KV-кэша.** Runtime-фильтр языка
  (`_generate_filtered`, §3.1) и весь механизм `concept_ids`/`attract_ids`
  (§6.1) устроены как ручной `eval`+`eval_logits` цикл с откатом состояния —
  это API одного процесса, у HTTP-сервера нет и не может быть эквивалента
  без переизобретения половины llama.cpp поверх HTTP.
- **Будущее подмешивание вероятностей (§10-обсуждение, не реализовано).**
  Обсуждавшаяся замена аддитивного attract на честную выпуклую комбинацию
  `p_final = (1-α)·p_natural + α·p_concept` (решает и калибровку веса, и
  зацикливание, см. находки в §10.3) **принципиально** требует доступа к
  `p_natural` до сэмплирования — то же самое ограничение, что и выше, только
  ещё жёстче: сервер не отдаёт полное распределение, только уже
  просэмплированный токен (или логиты топ-N через `logprobs`, чего
  недостаточно для честной смеси по всему словарю).
- **`VocabIndex`/dual-engine.** Работает через `embed_query`/`embed_batch` на
  живом Python-объекте движка (§5.5/§6.3) — реализуемо и через HTTP
  (`ServerEngine.embed()` уже так делал), но раз всё остальное всё равно
  требует in-process доступа, держать два разных пути ради одной функции не
  оправдано.

Иными словами: server-бэкенд был расcчитан на **exclude через logit_bias** —

## 12. Подмешивание вероятностей (`SemanticMix`) + групповая метрика для `SemanticFieldMeter` `[✑]`

Продолжение находки §10.3: аддитивный `attract` (`logits[t] += weight`) —
плохой инструмент. Нет естественного потолка (масштаб единиц зависит от
модели — `std≈2.9` у Qwen, вес `5.0` полностью разносил распределение),
поэтому либо слишком слабо (не перебивает тему), либо слишком сильно
(зацикливание на одном токене). План: заменить сдвиг логитов на честную
выпуклую комбинацию распределений — и на этой же геометрии (не на пороговом
cosine, как весь V3b/Фаза 4 до сих пор) наконец реализовать `SemanticFieldMeter`
из §6, которому нужна именно **область**, а не эвристика.

### 12.1 Подмешивание вместо сдвига

```
p_final = (1 - α) · p_natural + α · p_concept
```

- `p_natural = softmax(logits)` — обычное распределение модели на этом шаге.
- `p_concept` — распределение по полю концепта F_C (равномерное или взвешенное).
- `α ∈ [0,1]` — уже нормализованная сила эффекта, **не зависит от масштаба
  логитов конкретной модели** (в отличие от `attract_weight` в «сырых»
  единицах). `α=1` — модель обязана выбрать токен из F_C на этом шаге;
  `α=0.3` — мягкая подмешка. По построению `p_final` — валидное
  распределение (сумма = 1), выпуклая комбинация двух валидных распределений
  не может «разнести» вероятность так, как это делал неограниченный
  аддитивный сдвиг.
- Решает и находку §10.3(2) («attract слабый против контрастной темы»):
  можно контролируемо ставить `α` близко к 1 на первых токенах предложения
  («засеять» тему), а дальше давать модели дописывать естественно — то, что
  аддитивный вес не мог сделать без риска зацикливания.

### 12.2 Групповая метрика для поля F_C — важное уточнение

Изначальный план (озвучен в чате перед реализацией) был переиспользовать
`TokenGroup.project_per_token`/`tokens_in_coset`, которые уже существуют
(`groups/token_group.py`) и не используются нигде в продакшене (только тесты
и мёртвый `SemanticShift`, у которого нет вызывающего кода). **Проверка перед
реализацией показала, что `project_per_token` для этого не годится**:

```python
def project_per_token(self, logits):
    return (logits[:, None] * self._W[None, :] + self._b[None, :] > 0)
```

Элемент группы для токена `i` зависит от **текущего значения** `logits[i]` —
скаляра, который меняется на **каждом шаге генерации** (и меняет знак при
переходе logit'а через 0, что переворачивает добрую половину координат
проекции). Это годится для «отпечатка» состояния всего распределения на
шаге (`project(logits)`, уже используется как единая проекция всего вектора
— см. `ContextState`/`SemanticShift`), но **не** для определения поля
F_C — поле обязано быть стабильным, не пересчитываться заново на каждом
токене.

**Решение — новая, стабильная проекция от эмбеддинга, не от logits:**

```python
# TokenGroup (новый метод, отдельная от project()/project_per_token() матрица):
def project_embedding(self, embedding) -> np.ndarray:
    """sign(W_e · e + b_e), W_e/b_e фиксированы (seed), НЕ зависят от logits."""
```

`W_e`/`b_e` — отдельная random-матрица (свой seed-поток), размера
`(k, embed_dim)`, инициализируется один раз и не меняется. Тот же самый
токен с тем же эмбеддингом ВСЕГДА проецируется в один и тот же элемент
группы — вот что даёт «поле = coset» смысл, который был в §6.1 с самого
начала, а не то, что фактически делал `project_per_token`.

**`build_concept_field(tg, vocab_index, seeds, max_distance) -> Set[int]`**
(новый модуль `groups/semantic_field.py`):
1. `vocab_index.embeddings` (уже посчитаны и закэшированы, §5.5/§6.3) →
   `tg.project_embeddings_batch(...)` → элемент группы на каждый кандидат
   (один раз, кэшируется вместе с индексом).
2. Для каждого seed (прототип/лексикон концепта): `center =
   tg.project_embedding(vocab_index.embed_query(seed))`.
3. `tg.tokens_in_coset(center, elements, max_distance)` — **точное**
   булево множество, не порог по cosine. Объединение по всем seeds.

Это даёт именно то, что было целью §6.1: F_C — не эвристика, а область в
конечной группе с считающей мерой. Cosine-порог (`VocabIndex.nearest`,
всё ещё используется в V3a/V3b/Фазе 4, §5.5/§10) никуда не делся — это
разные, оба обоснованные способа задать поле; group-coset даёт точную меру
и составные операции (объединение/пересечение полей — групповые операции
над множествами элементов), cosine — более плавную/привычную настройку
через `min_similarity`.

### 12.3 `SemanticFieldMeter`

`p_concept` для подмешивания и метрика используют **одно и то же** F_C — не
два разных определения поля (что было бы несогласованно):

- `adherence(probs, field_ids) = Σ_{t∈F_C} p_t` — динамическая: сколько
  вероятностной массы модель кладёт в желаемое поле на текущем шаге (дуально
  к `leakage` для exclude, §6/§3.3).
- `coverage(field_ids, blocked_ids)` — статическая: какая доля F_C реально
  попала в маску/подмешку (`field_size`, `blocked_in_field`, `coverage_pct`).

### 12.4 Ограничение: только `LlamaCppEngine`

Подмешивание требует `p_natural = softmax(logits)` **до** сэмплирования —
то же ограничение, что уже привело к отказу от `server`-бэкенда (§11), только
жёстче: серверу неоткуда взять полное распределение по всему словарю (только
уже просэмплированный токен или top-N `logprobs`). Реализуется исключительно
в `LlamaCppEngine._generate_filtered` (единственное место с доступом к сырым
logits перед сэмплированием), новые параметры `generate(mix_ids=, mix_alpha=,
mix_weights=)`.

### 12.5 Интеграция с Фазой 4

`generate_guarded` (§10.1) для include-виолейшенов сейчас эскалирует
`attract_weight` (аддитивно, с потолком `max_attract_weight`). План — заменить
на эскалацию `mix_alpha` (природно ограничена `[0,1]`, потолок не нужен как
костыль — он уже встроен в само определение α). `attract_ids`/`attract_weight`
остаются в API (обратная совместимость, exclude-путь их не трогает); include-путь
переключается на `mix_ids`/`mix_alpha`.

### 12.6 Порядок реализации `[✓]`

1. `TokenGroup.project_embedding`/`project_embeddings_batch` (стабильная
   проекция, тесты на детерминированность/различимость).
2. `groups/semantic_field.py::build_concept_field` (coset через VocabIndex).
3. `engine/semantic_field_meter.py::SemanticFieldMeter` (`adherence`/`coverage`).
4. `LlamaCppEngine`: `mix_ids`/`mix_alpha`/`mix_weights` в `generate()` →
   `_generate_filtered` → новый `_mix_and_sample`.
5. `generate_guarded`: include-эскалация переключается на `mix_alpha`
   (только для `LlamaCppEngine`, fallback на `attract_weight` иначе).
6. Проверка на реальной модели (Qwen3VL + e5) — сделана, см. §12.7.

Все 6 пунктов реализованы и покрыты тестами (46 новых — `TokenGroup`
проекции, `build_concept_field`, `SemanticFieldMeter`, `_mix_and_sample`/
`_build_mix_probs`, интеграция с Фазой 4, `_filter_whole_word_tokens`).

### 12.7 Проверено на реальной модели — механизм подтверждён, поле оказалось узким местом

**Изолированно (юнит-тесты, без реальной модели): формула подмешивания
корректна.** `_mix_and_sample` не «взрывается» ни при каком масштабе логитов
(тест на logits со `std≈1000` — сильно преувеличенный аналог реальной
проблемы из §10.3 — проходит чисто), `α=0`/`α=1` дают ровно natural/concept
argmax, `α` вне `[0,1]` корректно клэмпится. Это было целью — и она
достигнута: калибровка веса под конкретную модель, которая ломала
`attract_weight`, здесь просто не существует как проблема.

**На реальной модели (Qwen3VL + e5) выяснилось: формула не главное — главное
поле.** Три отдельные находки, все про то, откуда берутся `mix_ids`, не про
сам механизм подмешивания:

1. **V3a (`ConceptSpec.to_token_ids`) непригоден для построения поля под
   подмешивание.** Токенизация многосложных русских слов через BPE
   естественно дробит их на фрагменты («кулинария» → «кулин»+«ария» и т.п.);
   лексикон из 5 слов дал 33 «сырых» ID, в основном однобуквенные
   Cyrillic-огрызки («т», «б», «а», «к», «е»). Подмешивание внедряет токен
   прямо в поток на **любой** позиции — огрызок, разумный только *внутри*
   слова, ломает синтаксис при `α` уже от ~0.2 (вывод превращался в
   «слоговый салат»). Exclude/attract (аддитивные) от этого не страдали,
   потому что огрызок там только конкурирует на своей позиции, а не
   становится «словом» сам по себе.
2. **Фикс — фильтр целых слов.** `_filter_whole_word_tokens` (новое,
   `guarded_generation.py`) оставляет только токены, чья сырая форма
   начинается с литерального пробела (маркер границы слова в BPE — начало
   нового слова, а не продолжение) и `len(strip()) >= 3`. На тех же 33
   «сырых» ID это дало 2 токена (`" рецепт"`, `" готов"`) — резко чище, но и
   резко *уже*.
3. **Даже с чистым полем маленького размера подмешивание всё равно
   скатывается в повтор при высоком `α`.** С полем из 2 токенов `α=0.15`
   давало связный текст с лёгким тематическим сдвигом; `α≥0.3` —
   зацикливание на «рецепт»/«готов» (тот же симптом, что убил
   `attract_weight` в §10.3, только через другой механизм). Значит:
   зацикливание — это не болезнь конкретно аддитивного сдвига, это болезнь
   **узкого поля** под сильным давлением, будь то сдвиг или подмешивание.
   Подмешивание чинит калибровку веса под модель — оно не чинит «поле из
   2 токенов недостаточно для естественной речи».
4. **V3b (`VocabIndex.nearest`, `min_similarity=0.55` по умолчанию) при
   вызове на неотфильтрованных BPE-фрагментах (не через `VocabIndex`'s
   собственный кандидатный пул, а как источник эмбеддингов для сравнения)
   давал 137 «кандидатов», среди которых почти не было относящихся к теме —
   `min_similarity=0.85-0.90` начинает резать мусор, но при малом
   `max_candidates` (800) в кандидатный пул физически не попадают нужные
   целые слова («блюдо», «кухня», «готовка» — все многотокенные, не входят
   в первые 800 по частоте). Это уже известная слабость V3b (§6.3), не новая.

**Вывод:** подмешивание — корректная, проверенная замена аддитивному сдвигу
именно там, где сдвиг был плох (масштаб/зацикливание из-за неограниченного
веса). Оно **не** решает более фундаментальную задачу — как надёжно собрать
достаточно широкое, чистое поле токенов для темы на морфологически богатом
языке. Это отдельная, не решённая в этой сессии задача (см. §12.8).

### 12.8 Комбинированный фикс — проверено, реальный прогресс с новым честным упором

Три вещи из §12.7 сделаны вместе на реальной модели: (1) `VocabIndex` теперь
по умолчанию требует `require_word_boundary` (фикс на уровне источника — см.
ниже), (2) `max_candidates` поднят с 800 до 6000, (3) `min_similarity` — с
0.55 до 0.85.

**Фикс источника: `VocabIndex.require_word_boundary` (default `True`, новый
параметр).** Старый фильтр кандидатов (`isalpha()` + `len>=2`) применялся
**после** `strip()` — а значит не отличал целое слово `" cook"` от осколка
`"ord"`: оба после strip выглядят как обычная алфавитная строка. Теперь
кандидат обязан **до** strip начинаться с литерального пробела (маркер
границы слова в BPE). Это чинит не только подмешивание — весь V3b
(`nearest()`, использующийся и в CLI/GUI-вкладке «Конструктор», §6.3/§7.1)
получает более чистый кандидатный пул. Тесты на дефолт/выключение
(`require_word_boundary=False`, старое поведение) + отдельный cache-key.

**Результат на реальной модели (кулинария, 6000 кандидатов, порог 0.85):**
поле выросло со 137 (в основном мусор) до 101 **осмысленных** слов после
фильтра целых слов: `cooking`, `breakfast`, `delicious`, `dining`, `recipe`,
`food`, `ingredients`, `menu`, `restaurant`, `tips`... Генерация при
`α=0.15-0.35` показывает **настоящий** тематический сдвиг без немедленного
распада: *"…dining with the family is always a good idea…"*, упоминания
`eating`/`recipes`/`meal`/`food` — то, чего не было вообще ни при узком поле
(2 токена), ни при грязном широком (137 огрызков). Это реальный прогресс, не
локальный шум — качественно другая картина, чем в §12.7.

**Но не решение, а сдвиг компромисса — два новых честных ограничения:**

1. **Кросс-языковое загрязнение.** e5 — мультиязычная модель; она сближает
   русские прототипы концепта с **английскими** словами в словаре Qwen
   (`cooking`, `food`, `recipe` — не `готовка`, `еда`, `рецепт`). Отсюда и
   переключение языка внутри русского ответа. Это не баг фильтра — это то,
   зачем вообще нужна кросс-языковая embedding-модель, только с побочным
   эффектом при подмешивании конкретно.
2. **Фильтр «только кириллица» возвращает узкое поле, а не чинит его.**
   Прямая проверка: тот же концепт, но кандидаты отфильтрованы до
   кириллических — из 101 остаётся **1** токен (`рецепт`). Результат — то же
   зацикливание, что и с узким полем в §12.7, сразу на `α=0.15`. Кросс-язык
   и есть источник ширины поля здесь; убрать его — вернуться к тому, откуда
   начали. Для по-настоящему широкого **русского** поля нужен либо
   существенно больший `max_candidates`, либо модель эмбеддингов с лучшим
   покрытием русской кулинарной лексики, либо не-token-level способ задать
   поле — ни то, ни другое, ни третье не реализовано.
3. **Высокий `α` (0.5+) всё равно скатывается в повтор**, независимо от того,
   насколько широко поле — просто «безопасный потолок» поднялся с ~0.1 до
   ~0.35. Это подтверждает вывод §12.7: зацикливание — свойство *силы*
   давления, не конкретно узости поля; более широкое поле отодвигает порог,
   не убирает эффект.

**Итог:** подмешивание с широким, отфильтрованным по границе слова полем —
измеримо лучше узкого или грязного поля, это не тупик. Но «широкое +
чистое по языку + без предела по `α`» одновременно не достигнуто ничем из
опробованного в этой сессии.

## 13. Найденная и исправленная причина «attract в 15 раз медленнее exclude» `[✓]`

Жалоба: подмешивание (attract/mix) работает (не считая зацикливания, §12.7-12.8),
но минимум в 15 раз медленнее exclude-режима. Проверено профилированием на
реальной модели — причина оказалась **не в математике подмешивания и не в
attract вообще**: она в одной строке, общей для ОБОИХ режимов, просто
attract сильнее по ней «размазан» из-за chunking в `generate_guarded` (§10.1).

**Находка:** `_generate_filtered` на каждый токен делал
`logits = np.array(self.llm.eval_logits[-1], dtype=np.float32)`.
`eval_logits` — свойство llama-cpp-python, его геттер:
```python
@property
def eval_logits(self):
    return deque(self.scores[:self.n_tokens, :].tolist(), maxlen=...)
```
Это конвертирует **весь** `scores[:n_tokens, :]` (растущий с каждым токеном!)
в Python-список через `.tolist()`, только чтобы вернуть последнюю строку.
Замерено изолированно: `eval_logits[-1]` — **~104мс/вызов**, сам forward
pass (`llm.eval([token])`) — **~6мс/вызов**. Чтение уже посчитанного
результата было **в 17 раз дороже**, чем его вычисление.

**Фикс** (`engine/llamacpp.py::_generate_filtered`): `self.llm.scores` —
уже numpy-массив; напрямую `self.llm.scores[self.llm.n_tokens - 1]` даёт ту
же строку без конвертации истории. Один `np.array(..., dtype=np.float32)`
после — копия одной строки (vocab_size,), не матрицы
(n_tokens × vocab_size). Побитово идентичный результат
(`np.allclose` → `True`), измеренное ускорение самого чтения — **160x**.

**Почему это раньше выглядело как «attract специфично медленный»:** оба
режима платят эту цену **на каждый сгенерированный токен** — но exclude
обычно идёт через один `engine.generate()` (весь ответ = одна серия
токенов), а attract/include шёл через `generate_guarded` (§10.1), который
генерирует **чанками**, и внутри каждого чанка — свой цикл по токенам,
платящий ту же цену заново на КАЖДЫЙ чанк. Больше чанков (короче
`chunk_tokens`, больше отказов) — больше раз посчитана одна и та же
дорогая операция. Не attract был медленным — оба были медленными
одинаково на токен, просто chunking умножал счётчик токенов эффективнее.

**Замерено до/после** (реальная модель, ~60 токенов, кэшированный
`VocabIndex`, без отказов guard'а):

| | до | после | ускорение |
|---|---|---|---|
| exclude (`engine.generate`, один вызов) | 6.13с | 1.27с | 4.8x |
| attract (`generate_guarded` + mixing) | 11.50с | 0.68с | 16.9x |
| соотношение attract/exclude | ~1.9x (на этом коротком прогоне; на более длинных/с отказами — заявленные ~15x) | **~0.5x** (attract даже быстрее в этом прогоне) | — |

Разрыв, из-за которого был задан вопрос, практически исчез — обе ветки
уложились в комфортный диапазон.

**Не тронуто, оставлено на будущее:**
- `logits_all=True` в конструкторе `Llama(...)` (`llamacpp.py`) — после
  фикса `eval_logits` в коде больше не используется вообще (грep
  подтверждает), флаг теперь избыточен. Не убран сейчас: может
  понадобиться для будущей «Real-time logits visualization в GUI»
  (tasks.md §9, нереализовано) — трогать по отдельному запросу.
- Переиспользование KV-кэша между чанками в `generate_guarded` (§9,
  пункт 2) — реальная, но теперь **гораздо менее заметная** неэффективность
  по сравнению с тем, что было (O(n²) по общей длине ответа остаётся, но
  константа на каждую переоценку упала на порядок вместе с этим фиксом).

## 14. GUI: include-режим и подмешивание в guard-концептах — ВЫПОЛНЕНО `[✓]`

`generate_guarded` (§10.1/§12) уже умел компилировать include-режимные
`guard.concepts` в `mix_ids` и эскалировать `mix_alpha`/`attract_weight` при
повторном нарушении — но GUI не давало способа создать такой концепт:
`_ConceptGuardDialog` жёстко ставил `mode="exclude"` и не имело поля
`lexicon`, так что ветка `if spec.mode in _INCLUDE_MODES` в
`generate_guarded` была недостижима из интерфейса (backend был реализован
и протестирован, интерфейс — нет).

**Что добавлено (`gui.py`):**
- `_ConceptGuardDialog`: выбор режима `exclude`/`include` + новое поле
  «Ключевые слова» (через запятую) — заполняет `ConceptSpec.lexicon`, из
  которого `ConceptConstructor.compile` строит стартовый набор токенов
  (V3a, без обязательного `vocab_index`). Обязательно для `include` —
  без лексикона `compile` вернёт пустой `mix_ids`/`attract_ids`, и
  эскалация будет работать вхолостую (в диалоге это заблокировано
  проверкой при OK).
- `_build_guard_section`: новые поля `threshold (include)`
  (`guard_include_threshold_var`, по умолчанию 0.55 — отдельно от
  exclude-порога, т.к. семантика разная, см. §5.1 докстринг
  `SentenceConceptGuard`), `mix_alpha`/`mix_alpha_step`
  (`LlamaCppEngine`), `attract_weight`/`attract_weight_step` (fallback на
  прочих движках) — все пробрасываются в `generate_guarded(...)`.
- `_generate_with_guard`: badge теперь показывает `[mix: N токенов]` или
  `[attract: N токенов]` по факту (`GuardResult.mix_ids`/`.attract_ids`),
  не только счётчик отклонений.
- `_refresh_guard_list` показывает режим и число ключевых слов на
  концепт.

Полный тест-сьют (123/1) без регрессий; GUI собран и проинстанциирован
headless без ошибок layout'а. Ручная проверка include-генерации на
реальной модели через сам GUI не проводилась в рамках этой правки (только
через прямой вызов `generate_guarded`, см. §12.7-12.9) — рекомендуется
перед тем как полагаться на неё в продакшене.
