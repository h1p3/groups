# План Б: автоподтяг контекста (Qwen 4B GGUF)

Динамический подтяг контекста без эмиссии запросов моделью.
Группа используется как механизм агрегации/забывания, а не валидации.

## Идея

Модель ничего не запрашивает. Ретривер сам смотрит на последние токены/эмбеддинг
генерации, решает, какие узлы гипертекста нужны, подтягивает их и агрегирует
через коммутативную групповую операцию. Контекст «сам» доезжает до модели.

- Подходит Qwen 4B: модель не тратит токены на агентный цикл и запросы.
- Контроль у пайплайна, а не у модели (4B не умеет в длинный агентный цикл).

## Цикл

```
состояние контекста h ∈ G
      │
      ▼
[модель генерирует шаг CoT]
      │
      ▼
[ретривер: эмбеддинг последнего сегмента генерации]
      │
      ▼
[скоринг узлов гипертекста]  ← косинус/релевантность
      │
      ▼
[выбор top-k]
      │
      ▼
[агрегация]  h' = h ⊕ вклад(выбранных узлов)
      │
      ▼
[забывание]  h'' = h' ⊖ вклад(устаревших/вытесненных из окна)
      │
      ▼
[инъекция в промпт]  h + топ-2 узла текстом, остальные — только h
      │
      ▼
[продолжение генерации] → следующий шаг → снова цикл
```

## Что даёт группа

1. **Коммутативность** — порядок подтяга узлов не влияет на состояние `h`.
   Гипертекст читается нелинейно, контекст от этого стабилен.
2. **Обратимость** — «забыть» узел без пересборки: `h'' = h ⊖ v`.
   Работает вместе со сдвигом KV-кеша: узел выпал из окна — вычли его след из `h`.
3. **Сжатие** — k узлов → один элемент `h`. В промпт тащится агрегат + 1-2
   фрагмента текстом, остальное — только вектор. Контекст вписывается в лимит токенов.

## Маппинг узлов в группу

- Элемент узла = детерминированный хэш-мэппинг: `node → g ∈ G`.
- `G = ℤ/nℤ` (счётчик-агрегат) или `ℝ^d` со сложением (тривиальная абелева группа).
- Вклад узла можно весить значимостью: `f(node, score) ∈ G`.

## Компоненты

```
src/context/
  store.py       # гипертекст-граф узлов (текст + эмбеддинг)
  puller.py      # ретривер: эмбеддинг последнего сегмента → скоринг → top-k
  aggregate.py   # h ⊕ вклады, вычитание узлов (группа)
  loop.py        # генерация ↔ автоподтяг ↔ инъекция в промпт
src/groups/
  map.py         # node → элемент группы (детерминированный маппинг)
  ops.py         # op / inverse для выбранной G
prompts/
  system.md      # правила роли
  cot.jinja      # шаблон CoT
scripts/
  serve.py       # llama.cpp server (context shifting, embedding mode)
  eval.py        # метрики подтяга (ниже)
config.yaml      # путь GGUF, top-k, лимиты, группа
```

## Эмбеддинги

- Эмбеддинг запроса — из того же GGUF (режим embedding) или от последнего
  сегмента генерации.
- Эмбеддинги узлов — предвычислены заранее (`store.py`).
- Один и тот же рантайм llama.cpp: генерация + эмбеддинги без второго сервера.

## Инъекция в промпт

- Окно ограничено: `система + h + текст топ-2 узлов + хвост генерации`.
- Сдвиг KV-кеша: при превышении лимита старое выпадает, его вклад вычитается из `h`.
- Частота автоподтяга: каждые N шагов / при падении уверенности / по порогу
  релевантности (порог ниже — не дёргаем модель зря).

## Constrained Decoding и Structured Output

### Роль в Плане Б

Модель НЕ эмитит запросы на подтяг (в отличие от Плана А) — поэтому CD/SO
используются не для ретрива, а для двух других целей:

1. держать CoT 4B-модели в формате (не дать ей «съехать» в длинном рассуждении);
2. выдавать машиночитаемый результат для пайплайна и eval.

### Constrained Decoding (CD) — GBNF-грамматики

- Каждый шаг CoT ограничен структурой: маркер шага + декларация элемента группы
  + свободная нарративная часть.
- Грамматика строится по `GroupSpec`: когда модель эмитит элемент группы, её
  допустимые токены ограничиваются синтаксисом этого элемента (например, цикловая
  нотация `(1 2 3)(4 5)` или `ℤ/nℤ: значение ∈ 0..n-1`).
- На этом уровне возможно и membership-ограничение: для `ℤ/nℤ` грамматика
  перечисляет только валидные значения — невалидный элемент физически
  не может быть сгенерирован.
- Нарратив шага остаётся свободным (иначе CoT превратится в шаблон, а 4B
  станет хуже рассуждать).

Пример структуры шага:

```
Шаг 2:
element: (1 2)(3 4)
narrative: свожу произведение к произведению транспозиций...
```

Грамматика разрешает любую нарративную строку, но `element:` принимает только
грамматически валидный элемент.

### Structured Output (SO) — JSON-схема

- Финальный ответ обязателен как JSON по Pydantic-схеме:

```json
{
  "answer": "окончательный элемент",
  "steps": [
    {"n": 1, "element": "…", "note": "…"}
  ],
  "context": {
    "h": "агрегат контекста после подтяга",
    "pulled": ["id узла 1", "id узла 2"]
  }
}
```

- Схема → GBNF (конвертер XGrammar или ручные построители) — модель вынуждена
  генерировать только валидный JSON; парсинг в пайплайне без дебага мусора.
- Поле `context.pulled` фиксирует, какой контекст реально был подтянут на
  последнем шаге — нужно для метрик и абляций eval.
- Ground-truth для eval вычисляется детерминированно (SymPy-операции группы),
  без второго LLM-оракула.

### Где это ложится в пайплайн

```
[шаг CoT] → CD: grammar ограничивает element-строку шага
    │
    ▼
[автоподтяг] → результат фиксируется в context.pulled (SO)
    │
    ▼
[финальный ответ] → SO: JSON-схема (schema→GBNF)
    │
    ▼
[eval] → парсинг JSON + детерминированная проверка
```

### Чего специально НЕТ

- Никакого CD для эмиссии ретрив-запросов — модель ничего не запрашивает,
  подтяг автономен (ретривер).
- Никакой валидации групповых аксиом — группа в Плане Б это механизм
  агрегации/забывания, а не проверки корректности.

## Метрики (eval.py)

- Доля шагов, где автоподтяг изменил `h` (активность подтяга).
- Токены контекста на шаг (сжатие vs полный текст узлов).
- Средний score подтянутых узлов (релевантность).
- Качество ответа: task accuracy на наборе задач с известным ground truth.
- Абляция: автоподтяг вкл/выкл, top-k = 1/2/5, частота подтяга.

## Этапы

1. **store + map**: граф узлов, эмбеддинги, детерминированный маппинг в G.
2. **aggregate**: op/inverse, вычитание узлов, unit-тесты (pytest).
3. **puller**: эмбеддинг сегмента → скоринг → top-k.
4. **loop + serve**: llama.cpp server, инъекция в промпт, сдвиг окна.
5. **eval**: метрики, абляции, тюн порогов.

## Риски

- **Семантический дрейф**: эмбеддинг последнего сегмента может не отражать
  реальную потребность → пороги релевантности и частота подтяга.
- **Мусорный подтяг**: нерелевантные узлы засоряют `h` → вклады взвешивать
  score-ом, старые узлы вычитаются по инверсии.
- **Двойная стоимость**: эмбеддинг запроса каждые N шагов → кешировать,
  пересчитывать только при значимом сдвиге.
